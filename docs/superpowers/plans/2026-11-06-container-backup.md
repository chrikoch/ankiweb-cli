# Containerized AnkiWeb Backup Implementation Plan

> **For agentic workers:** Use superpowers:executing-plans or the execution method selected by the user. Work through the checkboxes in order, record actual results, and follow the user's instructions about pauses and commits.

**Goal:** Run the existing `ankiweb-backup` command in a container with a writable host backup directory and a read-only host credentials file, without installing Python or creating a virtual environment on the target host.

**Architecture:** Build a Linux container image containing Python and the existing project with its runtime dependencies. The image invokes the existing CLI; it does not implement its own backup, synchronization, scheduling, or credential management. Validate the image and mounts using synthetic data, then publish an `amd64`/`arm64` image to the public GitHub Container Registry after successful checks on `main`. The existing native CLI remains available.

**Tech stack:** Docker-compatible OCI image, Python, existing Anki library and CLI, GitHub Actions, pytest. Docker is the initial documented runtime; do not claim Podman compatibility without testing it.

**Spec:** This plan records the agreed scope from the conversation; `requirements/ankiweb-backup.md` remains authoritative for backup behavior. The user described a container launched with a mounted destination directory, and approved public GHCR publication from CI; the separate read-only credentials mount follows the existing command's requirements.

## Scope and constraints

- Target Linux `amd64` and `arm64`; ARM64 CI or emulation does not replace a real Raspberry Pi test.
- Preserve the existing backup's download-only request restrictions, snapshot checks, error handling and no-overwrite guarantees. Do not change production backup behavior simply to make container testing easier.
- Do not put real credentials or collections into the image, build context, logs or repository. Use dedicated synthetic fixtures and a test-only credentials file.
- Prefer an unprivileged container process. Verify actual host UID/GID mapping, permissions on an existing `0600` credentials file, and output ownership; do not weaken file permissions to make a test pass. Document rootless Docker or user-namespace limitations when observed.
- User-managed scheduling remains outside the image; no cron daemon, startup service, retention policy, Compose setup, custom orchestration or new restore functionality is requested.
- Build and test pull requests without publishing. After all required tests pass on `main`, publish `ghcr.io/chrikoch/ankiweb-cli:latest` and a commit-specific tag; image digests provide immutable references. The user has authorized public GHCR image publication as part of this plan. Git pushes, merges and commits still require explicit user instruction.
- Only mark a checkbox complete when its checks have actually passed. Record unavailable environments, skipped tests and unverified behavior as open; do not claim a CI pass from local emulation.
- The earlier plan's Raspberry Pi, cron and post-restart acceptance checks were explicitly deferred by the user and remain open; this work must not mark them complete without performing them.

## Files and interfaces

- Create `Dockerfile`: build an image with the existing CLI as its entrypoint; `docker run IMAGE ankiweb-backup ...` passes arguments to `ankiweb-cli`.
- Create `.dockerignore`: restrict build context to the files needed to build the package; exclude credentials, backup output, Git metadata and local environments. Ensure all build inputs used by `pyproject.toml`, including `README.md` and `LICENSE`, remain available.
- Modify `.github/workflows/test.yml`: retain the existing OS/Python jobs and add Linux image build and runtime checks on available x86-64 and ARM64 runners. Add a publication job or workflow that runs only for a successful `main` build and publishes the same tested revision to GHCR.
- Modify `README.md`: add build, invocation and operational instructions while preserving native installation and backup instructions.
- Add focused container-test helpers only if required to exercise the actual image; keep them under `tests/` and reuse existing synthetic server fixtures. Do not ship test helpers or development dependencies in the runtime image unless justified by an observed requirement.
- Create `docs/superpowers/plans/container-backup-acceptance.md` to record actual runtime, architecture, permissions, tests and limitations.

## Review focus

The checks below must cover at least these cases: credential exposure in image layers or build context; mismatched host/container identity; missing, unreadable or insecure credentials; output collisions or unwritable mounts; and interrupted or failed backup publication. Also verify that containerizing does not cause forbidden network requests or alter exit codes.
