# AnkiWeb backup: detailed design draft

Status: **reviewed design**, with implementation details and explicit gaps carried into the remaining plan points. The user has agreed to a plaintext credentials file for this command, documented residual uncertainty after successful checks, and a small custom Anki protocol client built with existing HTTP/compression libraries. The requirements and [feasibility findings](ankiweb-backup-feasibility-design.md) remain authoritative. Real AnkiWeb, target-Pi reboot/cron and current Anki Desktop acceptance checks remain open.

## Proposed file boundaries and interfaces

Follow the existing module layout. Names and signatures here are proposals to make the design reviewable; adjust only through the detailed implementation plan.

| File | Responsibility and interface |
| --- | --- |
| `src/ankiweb_cli/cli.py` | Add Click command `ankiweb-backup` with required `--output-dir` and `--credentials-file`, `--attempts` default 3, and `--max-retry-delay` in seconds default 60. Reject attempts below 1 and delay caps below 5. Ensure all command errors, including argument-validation errors, reach stdout without credentials; do not echo untrusted argument values or raw library errors. Preserve existing commands. |
| `src/ankiweb_cli/backup_credentials.py` | `load_credentials(path: Path) -> BackupCredentials` parses UTF-8 TOML with `[ankiweb]` keys `username` and `password`, validates nonempty strings and a regular file, and on Linux checks group/other permission bits. Users must configure protection themselves on Windows and macOS. Never include secret values, file contents, or parser excerpts in exceptions. |
| `src/ankiweb_cli/ankiweb_reader.py` | `AnkiWebReader` provides `login(username: str, password: str) -> None`, `collection_meta() -> CollectionMeta`, `download_collection(destination: Path) -> None`, `media_usn() -> int`, `media_changes(after_usn: int) -> list[MediaChange]`, `media_sanity(file_count: int) -> bool`, and `download_media(names: list[str], destination: Path) -> set[str]` returning the names received. The proposed HTTP allowlist is `hostKey`, `meta`, `download`, `begin`, `mediaChanges`, `downloadFiles`, and the media count check `mediaSanity`. |
| `src/ankiweb_cli/ankiweb_backup.py` | `run_backup(output_dir: Path, credentials: BackupCredentials, attempts: int, max_retry_delay: float, report: Callable[[str], None]) -> Path` owns fresh attempt workspaces, validation, retries, package export, collision-safe publication and cleanup. Split internals if necessary; no interaction with the normal local collection. |
| `tests/test_backup_credentials.py`, `tests/test_ankiweb_reader.py`, `tests/test_ankiweb_backup.py`, `tests/test_cli.py` | Test the corresponding public behavior and use a local allowlisting server with synthetic data for protocol, recovery, no forbidden requests and restore tests. |

`BackupCredentials` contains only `username` and `password`; its string representation must not reveal either. `MediaChange` contains filename, server USN and SHA-1 (empty for a deletion); `CollectionMeta` contains the modification time, schema time and collection USN. The media USN is obtained separately through `begin` and compared separately. Exact types and field names must be defined consistently before implementation. Keep authentication keys out of error text and public results.

## Credentials and platform behavior

The user agreed to this TOML credentials file format:

```toml
[ankiweb]
username = "your-ankiweb-email"
password = "your-password"
```

On Linux, inspect the opened file and reject group/other permission bits; `0600` is the documented setup. Avoid printing parser excerpts or raw dependency exceptions that could contain credentials. The credentials file is never included in the package and should be excluded from filesystem backups. Tests use synthetic values. On Linux filesystems with POSIX ACL semantics, the group bits restrict effective named-user and group ACL entries; this does not establish equivalent behavior on every filesystem. On Windows and macOS, the user agreed that the command will not automatically verify permissions; document how users restrict access and that incorrect permissions can go unnoticed. On macOS, ACLs can grant permissions beyond mode bits. The available low-level libraries and their gaps are documented in `ankiweb-backup-platform-libraries-review.md`.

## Transport, redirects and data handling

- Propose `httpx` for HTTP and `zstandard` for protocol compression; verify compatible versions and ARM64 wheels before choosing dependency bounds. Use an explicit operation allowlist, not a general-purpose sync function. Only the approved methods above may be invoked by backup code.
- Disable automatic redirects. Resolve relative `Location` safely; before forwarding the password or hkey require an explicitly trusted target and a finite redirect limit. Proposed initial production policy: HTTPS with an AnkiWeb hostname and trusted port, checked against existing endpoint configuration. Implement and test this conservative policy with synthetic redirects; actual AnkiWeb hostname behavior remains an acceptance test with the separate account and compatibility must not be claimed before that test. Test disallowed schemes, hosts, ports, malformed values, loops and no secret sent to a rejected target. An injected loopback policy may be used only in synthetic tests.
- Encode the selected protocol version, JSON bodies and Anki sync headers as documented by the investigated source. Stream large collection, compressed and media ZIP responses to temporary files instead of buffering entire payloads in RAM; validate framing/size when available, reject errors and truncation, and never silently treat an invalid response as complete. Test representative large synthetic collections and media on constrained hardware; do not set arbitrary size limits that silently exclude valid backups. Test login, 308 behavior, error responses and compression separately. A real AnkiWeb sequence still requires the agreed separate test-account acceptance check.
- Validate server-supplied filenames and archive metadata before writing. Reject path traversal, invalid names, duplicate or unexpected entries, collisions and missing/partial data. Do not silently rename or skip an AnkiWeb file. Download in batches of at most 25, repeat a partial batch for its outstanding filenames, require progress and verify every returned file against its listed SHA-1. Start enumeration at `lastUsn=0` and continue through an empty page; reject non-advancing or nonmonotonic pages. The server USN obtained from `begin` is a separate baseline for change detection, not the enumeration cursor. A monotonically increasing response does not itself prove the remote index is complete, so retain the documented residual limit.
- A local Anki 26.9.3 synthetic-server test on Linux uploaded and downloaded both `Test.png` and `test.png` with different contents. A separate local test using Anki's standard `include_media=True` export and backend import preserved both files and their original note references on a case-sensitive Linux filesystem; an independent reviewer reproduced this. These current names can collide on case-insensitive filesystems; the legacy-name exclusion below does not cover them. The user chose the simpler approach: preserve both names where the executing filesystem permits, and otherwise fail with a clear conflict without renaming, overwriting or omitting files. Add tests of both behaviors and document the limitation, including restoration on a case-insensitive filesystem. [Anki's manual](https://github.com/ankitects/anki/blob/main/docs-site/manual/media.mdx) describes cross-platform filename handling, but does not establish that every remote state can be represented on every local filesystem.
- An isolated probe exported the collection without media using Anki 26.9.3, then constructed a modern package with numbered ZIP entries and Anki's `MediaEntries` protobuf/zstd format for those two names. Anki's backend restored both media bytes and their unchanged note references on case-sensitive Linux. This is only a feasibility experiment, not the selected approach: it requires additional application logic, has not been tested on Windows or macOS, and cannot itself make a case-insensitive restore destination represent both names.
- Anki's [media source](https://github.com/ankitects/anki/blob/29bb700b951e3f0c0cb69b77c0180fc1fe33e6ba/rslib/src/media/files.rs) says older AnkiWeb data may contain names that current normalization would change. On Linux with Anki 26.9.3 and synthetic data, the modern exporter rejected both `CON.jpg` and an NFD-form `é.png`. Anki's `media.check()` renamed `CON.jpg` to `con_.jpg` and updated a test note's image reference, but left references in a card template and CSS unchanged, breaking them after restore. The user decided to assume such legacy names are absent and exclude special handling for now. If encountered, fail clearly without silently renaming or omitting media. The separate decision for otherwise valid case-colliding names is described above.
- The inspected `mediaChanges` server SQL has no explicit `ORDER BY`; a local SQLite test produced reversed results when unordered results were reversed. Reject non-increasing results, and use the separately tested `mediaSanity` count check as an additional completeness check. A matching count and monotonic pages still do not prove index or snapshot completeness; see `ankiweb-backup-platform-and-paging-review.md`. Never use fastanki's high-level media sync or ordinary Anki media sync for backup.

## One attempt and change checks

1. Create an isolated temporary workspace inside the existing output directory, with no credentials file inside its media directory. This places the temporary package on the output filesystem for publication. Authenticate and fetch collection/media metadata using the allowlisted reader. Record the initial media USN.
2. Download the raw collection and check that it opens as the expected Anki/SQLite database and passes integrity checks. Read its collection modification/schema/USN values **before** any local Anki operation could modify them.
3. Enumerate live media entries from the beginning, treating remote deletion records as absent, then download and validate all listed files as described above. Print individual filenames and stage progress, with credential/token values redacted.
4. Compare the number of validated live files with the server-maintained count using `mediaSanity`, then re-read media USN and remote collection metadata. A count mismatch, changed media USN or a mismatch between the raw downloaded collection's modification/schema/USN and the final remote metadata fails the attempt. This comparison was demonstrated on local servers but is still a **candidate**: validate semantics for each supported Anki version and the actual AnkiWeb server before relying on it. Own/other downloads may alter metadata and cause retries. A required metadata or integrity check that cannot run fails the attempt, not a silent pass.
5. With all checks passed, use Anki's modern collection-package export with media on the temporary collection. Verify that the resulting archive is readable and its modern collection and media manifest match the expected collection and validated media set, including filename mapping and media bytes/checksums; a synthetic restore test must verify scheduling, review history, referenced and unreferenced media. Export cannot itself prove remote completeness.
6. Publish the finished package to the existing output directory using a UTC timestamp and a unique collision suffix. First use supported no-replace operations on the completed, closed temporary package, such as Linux `renameat2(RENAME_NOREPLACE)` or a hard link; both passed local ext4 collision probes. If no suitable no-replace publication operation is supported, the user accepts exclusively creating a new final filename and copying the validated temporary package into it. Use exclusive creation, never a check followed by overwrite; a collision selects another name. In this fallback the final name is visible while copying, and a crash can leave an incomplete `.colpkg`. Report success only after the copy and close complete; report copy errors, and clean up an incomplete file when safely possible. The exporter itself must not write to the final filename because it can overwrite. The exact platform methods and exclusive-creation behavior on network filesystems remain to be verified; see `ankiweb-backup-platform-libraries-review.md`.

Checks reduce risk but do not produce an atomic collection/media snapshot or prove the server's index contains every file. The user explicitly accepts a successful backup with that documented residual uncertainty when every required check passes. An item that changes without advancing observable metadata may evade detection.

## Retries and output

Validate arguments and credentials before the attempt loop. Each attempt gets a new workspace and cleans up on failure. Every attempt failure, including a detected remote change or a failed required check, reports a sanitized error and retries until the configured total is exhausted. Wait `min(max_retry_delay, 5 * 2**(retry_number-1))` seconds before retry numbers 1, 2, and so on. Report exhaustion as a nonzero exit; report the completed path only after publication. Validate `attempts >= 1` and `max_retry_delay >= 5`. An interruption can leave temporary artifacts; when exclusive-copy fallback is used it can also leave a partial final `.colpkg`, as accepted by the user.

Treat publication as a separate state: after a no-replace operation is known to have published the validated package, report that path even if subsequent temporary-file cleanup fails, and emit a warning rather than download and publish another package. A directory-sync failure must also be reported, with the durability uncertainty; it must not cause an existing final file to be overwritten. A network filesystem may report an error even when it performed a rename, so reconcile an ambiguous outcome before another publication, without assuming that a file at the name belongs to this attempt. If the outcome cannot be established, report the uncertainty and any relevant path; retry reconciliation within the configured attempt limit instead of silently creating a second completed package. The platform-specific evidence needed to identify an ambiguous result, the exact cleanup and sync handling, and corresponding failure-injection tests remain implementation tasks; do not claim these cases are already solved.

## Anki versions and platform evidence

- Baseline constraint in `pyproject.toml` remains `anki>=24.0`; do not narrow it for the entire CLI. **24.11 and 26.9.3** are the initial implementation and CI test points, with 26.9.3 the primary candidate for the user's Pi. This is a test selection, not a claim that every intervening or future version is supported, nor a prohibition on using other versions. Establish and document support from the implementation and target-platform acceptance tests; current evidence cannot establish a continuous supported range.
- On x86_64 Linux/Python 3.13.5, the pre-implementation suite passed **77 tests with Anki 24.11**, and the synthetic modern-package roundtrip passed with 24.11 and 26.9.3. Six local synthetic protocol/change scenarios passed on both servers. These tests used temporary probes and do not establish actual AnkiWeb compatibility, current Desktop UI import, or behavior of a future backup implementation.
- The user's Raspberry Pi reports Debian 13.7, ARM64, glibc 2.41 and Python 3.13.5, compatible with the published 26.9.3 ARM64 wheel's tags; installation and operation on that Pi remain to be tested. The existing CI checks Linux x86_64 with Python 3.11 and 3.12. Focus manual checks on Linux and the target Pi, and add Windows and macOS builds and automated CI checks alongside Linux ARM64 and Python 3.13 where dependencies and runners permit. Document that Windows and macOS receive less manual testing and preserve existing supported combinations; published wheels alone are not runtime evidence.
