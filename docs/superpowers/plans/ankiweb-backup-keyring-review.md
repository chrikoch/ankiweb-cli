# Headless keyring feasibility: partial results

Investigated on 2026-11-02 with synthetic credentials only. The test environment was Debian 13, x86_64, Python 3.13.5, running under WSL2; it was not a Raspberry Pi. Python packages included `keyring` 25.7.0 and `SecretStorage` 3.5.0. Debian's GNOME Keyring 48.0 was downloaded and unpacked into `/tmp`, not installed system-wide. Temporary data, configuration and runtime directories and a separate D-Bus session prevented use of the user's real keyring. No actual AnkiWeb password was used.

## Observations

- Before starting the isolated service, `python -m keyring --list-backends` reported only the fail backend and disabled chainer. The project's `keyring` Python dependency by itself did not provide a usable secret service in this environment.
- With `DISPLAY` and `WAYLAND_DISPLAY` unset, an isolated D-Bus session and `gnome-keyring-daemon --unlock --daemonize --components=secrets`, the SecretService backend was selected. The project's `store_password()` and `get_password()` successfully stored and retrieved a synthetic value. The test supplied a synthetic unlock passphrase to the daemon; it did not solve unattended passphrase provisioning.
- After ending that D-Bus session and starting a new session and daemon **without unlocking**, retrieval of the previously stored synthetic secret failed with `KeyringLocked`. This simulates a service/session restart, not a machine reboot.
- In another fresh session, supplying the synthetic passphrase to unlock the service allowed a separate process with a minimal cron-like environment and the session's `DBUS_SESSION_BUS_ADDRESS` to use the project's `get_password()`. The same kind of process without that bus address failed with `NoKeyringError`. This was a direct process started with a minimal environment, **not a cron job**.

The [keyring documentation](https://keyring.readthedocs.io/en/stable/#using-keyring-on-headless-linux-systems-in-a-docker-container) likewise describes a Secret Service with D-Bus, an unlock operation and an application in the same D-Bus session. The tests above do not show that such a session starts, unlocks and stays available automatically after a real reboot or under cron.

## Outstanding requirements

A real reboot, an actual cron invocation after reboot, and a headless Raspberry Pi test have not been performed; no Raspberry Pi is available in this environment. Consequently unattended use of the existing keyring approach on the target is **not yet established**. In particular, the method and security tradeoff for providing an unlock secret at boot remain unresolved. A keyring test using a blank passphrase or storing an unlock secret is not automatically an acceptable substitute for the existing credential requirements.

These findings motivated the alternatives review below. Following the decision recorded at the end of this document, acceptance must instead verify the selected credentials-file approach after a real reboot and from cron, including failures when the file is unavailable or insufficiently protected. The temporary `/tmp/ankiweb-keyring-probe/` scripts and test data are disposable and do not constitute production setup.

## Alternatives for unattended access

The following is a documentation and source review, not a proven configuration on the user's Raspberry Pi. The requirement explicitly includes execution from cron after reboot; replacing that with a systemd timer alone would not verify or satisfy that requirement. The comparison below was written before the subsequent user decision; no approach has been implemented.

| Approach | Boot and cron implications | Security and project implications |
| --- | --- | --- |
| Existing keyring with GNOME Secret Service | An unlocked service and an accessible D-Bus session are needed. GNOME's PAM integration can unlock the login keyring with a password supplied during login; unattended boot cannot assume such a login or its password. The synthetic minimal-environment test did not establish a real cron setup. | Keeps the existing project API and OS-keyring approach. Fully unattended unlocking still requires an independently available unlock secret or another deployment-specific mechanism. [Keyring docs](https://keyring.readthedocs.io/en/stable/#using-keyring-on-headless-linux-systems), [GNOME PAM docs](https://wiki.gnome.org/Projects/GnomeKeyring/Pam). |
| `keyrings.cryptfile` backend | Supports a file-backed encrypted keyring and accepting its master password from an environment variable. A scheduler still needs a source for that master password after reboot. | Reuses Python's keyring interface but adds a third-party backend and a separate key-provisioning problem; putting the master secret in an ordinary cron entry or an accessible file defeats much of the encryption. No compatibility or Raspberry Pi test was performed. [Upstream README](https://github.com/frispete/keyrings.cryptfile/blob/39c01c8c8d85b32df13ee89615fde5d1c02ecaa2/README.md). |
| systemd encrypted credentials | `systemd-creds` and `LoadCredentialEncrypted=` can bind stored credentials to a host key, TPM2, or both and deliver them to a systemd service. Availability depends on the installed systemd version, configuration and hardware. A systemd timer alone is not a cron test; a cron-triggered service and its authorization would need a separately demonstrated setup. | A service could potentially receive either the AnkiWeb credential directly or a secret to unlock a keyring. Both need integration and a concrete design; the existing CLI reads the password through keyring and does not consume a systemd credential. A host key stored on the same disk does not protect against an attacker who can read both the ciphertext and host key; TPM protection depends on hardware and configuration. System/root or authorized access can still retrieve service secrets. No target test performed. [systemd-creds](https://www.freedesktop.org/software/systemd/man/256/systemd-creds.html), [systemd.exec](https://manpages.debian.org/trixie/systemd/systemd.exec.5.en.html). |
| Protected plaintext credential file or blank keyring password | Can support unattended cron after reboot without an interactive unlock, subject to permissions and availability. | This weakens at-rest protection and is inconsistent with the existing README's no-plaintext-credentials statement unless the user explicitly accepts a change. An empty GNOME keyring password means unencrypted on-disk storage according to [GNOME](https://wiki.gnome.org/Projects/GnomeKeyring/StoringSecrets). Do not introduce either silently. |
| Manually unlock an encrypted keyring after boot | Works only after a human supplies the unlock secret and a cron process reaches the unlocked session. | This does not meet the requested unattended operation immediately after an unassisted reboot; it may be a useful operational fallback only if the user accepts that limitation. |

The comparison informed the decision below. A real AnkiWeb test account is a separate question; the selected credentials-file approach can be tested with synthetic credentials. Do not assume the target Pi has a TPM, user-level systemd credentials, or an unlocked desktop keyring after boot.

## Decision following the investigation

The user chose a plaintext credentials file for the new backup command, with its path specified on invocation and restrictive access permissions. The username and password will be read from that file; existing commands retain their OS-keyring behavior. Documentation must explain plaintext storage and exclusion of the credentials file from backups. The exact file format and validation details remain part of implementation planning. The selected approach still requires verification on the target after a real reboot and from an actual cron job; the earlier keyring tests are not evidence of that.
