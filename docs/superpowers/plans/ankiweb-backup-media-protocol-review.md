# Anki media download: source review and isolated probe

Reviewed Anki 24.11 at commit `8e5efc597dd61a91cea21beacddf312ad1ffea9b`, and the relevant server files at 26.09.3 commit `29bb700b951e3f0c0cb69b77c0180fc1fe33e6ba`. The isolated runtime probe used the PyPI `anki` package 26.9.3 on Linux/Python 3.13.5, with a synthetic Anki server and no AnkiWeb credentials or connection. Findings describe these versions and do not establish how AnkiWeb itself behaves.

## Source findings

- The protocol exposes POST `/msync/begin`, `/msync/mediaChanges` and `/msync/downloadFiles` separately from `/msync/uploadChanges` ([protocol](https://github.com/ankitects/anki/blob/29bb700b951e3f0c0cb69b77c0180fc1fe33e6ba/rslib/src/sync/media/protocol.rs)). The public `Collection.sync_media()` runs the ordinary media sync, which can upload pending changes and deletions; it is not a download-only API ([syncer](https://github.com/ankitects/anki/blob/29bb700b951e3f0c0cb69b77c0180fc1fe33e6ba/rslib/src/sync/media/syncer.rs)). No supported Python API for the individual media requests was identified in the inspected `Collection` and backend service interfaces.
- `begin` returns the server media USN. `mediaChanges` accepts `lastUsn` and returns filename, USN and SHA-1; an empty digest represents a deletion. The server query returns at most 1,000 rows after the requested USN. The ordinary client advances to the last returned USN until an empty page ([query](https://github.com/ankitects/anki/blob/29bb700b951e3f0c0cb69b77c0180fc1fe33e6ba/rslib/src/sync/media/database/server/entry/changes.sql), [client](https://github.com/ankitects/anki/blob/29bb700b951e3f0c0cb69b77c0180fc1fe33e6ba/rslib/src/sync/media/syncer.rs)). The query does not explicitly specify an order; completeness under all database states and concurrent changes needs further analysis.
- `downloadFiles` takes names and returns a ZIP whose `_meta` maps ZIP entry names to actual filenames. The inspected server accepts at most 25 requested files and can return fewer than requested once approximately 2.5 MiB is reached; a caller must detect omissions and continue ([download](https://github.com/ankitects/anki/blob/29bb700b951e3f0c0cb69b77c0180fc1fe33e6ba/rslib/src/sync/media/database/server/entry/download.rs), [ZIP format](https://github.com/ankitects/anki/blob/29bb700b951e3f0c0cb69b77c0180fc1fe33e6ba/rslib/src/sync/media/zip.rs)). The digest from the listing permits checking the bytes downloaded; mismatches must not be silently accepted.
- A requested file missing from the server filesystem can cause the open-source server to remove its media database entry and return a conflict ([handler](https://github.com/ankitects/anki/blob/29bb700b951e3f0c0cb69b77c0180fc1fe33e6ba/rslib/src/sync/http_server/media_manager/download.rs), [database](https://github.com/ankitects/anki/blob/29bb700b951e3f0c0cb69b77c0180fc1fe33e6ba/rslib/src/sync/media/database/server/entry/download.rs)). This is an additional limit on a strict read-only claim; it is not evidence of AnkiWeb's implementation.

## Local probe

A throwaway Python probe under `/tmp/ankiweb-media-probe/probe.py` started the official `anki.syncserver` on loopback with synthetic credentials and a temporary data directory. It prepared two synthetic files by using ordinary media sync **only against that local server**; one filename appeared in a local synthetic note and the other did not. The collection was not uploaded to the server. A throwaway client then used direct protocol calls through a local proxy that allowed only the three media read endpoints and rejected other requests. A front proxy returned a synthetic 308 redirect for `/sync/meta`, whose target the probe used as the media endpoint.

The observed backup-side sequence was `/sync/meta` at the front proxy, followed at the target by `/msync/begin`, two `/msync/mediaChanges` calls (one nonempty and one empty), and `/msync/downloadFiles`. Both original filenames and bytes were returned, and their SHA-1 digests matched the listed digests. The proxy observed no media upload or delete request in this sequence. The commands completed successfully on 2026-11-02. A local-only network exception was necessary because the default sandbox disallows loopback sockets; the `zstandard` dependency was installed in a temporary uv environment for this probe.

A second isolated run used `/tmp/ankiweb-media-probe/multipage.py`, the same Anki server and proxy, and 1,004 synthetic files including one 3 MiB file. It received three `mediaChanges` responses (two nonempty and one empty) and used 42 `downloadFiles` requests. The oversized file forced at least one partial ZIP response. The probe verified every filename, byte sequence and listed SHA-1 digest, and the proxy accepted only the listed read endpoints. Fixture creation again used ordinary media sync exclusively against the synthetic server. Both the server and proxy were bound to loopback.

A third isolated run (`/tmp/ankiweb-media-probe/error_cases.py`) deliberately changed one synthetic server file after enumeration, then downloaded it and compared its SHA-1 to the previously listed digest. The mismatch was detectable. It then removed a different server file directly on disk before requesting it; the server returned HTTP 409 and a fresh enumeration no longer contained that file. This confirms the inspected server's missing-file index removal in this synthetic case. The probe checked the mismatch itself; it did not test failure handling or retries in a production backup client. The observed backup-side requests used only the same allowed endpoints.

A fourth local run (`/tmp/ankiweb-media-probe/concurrency.py`) used a separate ordinary media sync against the synthetic server to add a file and replace another after initial enumeration. The server media USN changed from 2 to 4, both names appeared in `mediaChanges` after USN 2, and the changed file no longer matched its original digest. This supports detecting those particular concurrent changes by comparing media USNs or file hashes. In the same run, removing another file directly from the synthetic server filesystem and requesting it caused HTTP 409 and index removal, but the server media USN stayed at 4. A USN comparison alone therefore did not detect that server-side index change.

In the first attempt at this test, a very fast local file replacement was not included by the fixture client's sync; only the newly created file appeared. The successful rerun set the modified file's mtime five seconds ahead of its original value. This observation suggests a timestamp-related fixture limitation; its exact cause was not established. The checks do not establish an atomic collection-and-media snapshot: a change after the final observation remains outside that observation, and server changes that do not advance the media USN can escape a USN-only check.

These runs verify a hand-written experimental client against one local server and simulated redirect. They do **not** prove actual AnkiWeb redirects or missing-file behavior, reliable detection of all changes during download, completeness under all server database states, or a production implementation. The probes are temporary, not a supported implementation or a replacement for automated network-level regression tests.

## Consequences

A direct-protocol approach is plausible but requires custom protocol handling, validation, paging, redirect handling and error handling; no choice has been made to adopt it. A read-only supported Anki API or suitable existing library has not yet been established. Assess these alternatives, the missing runtime cases and consistency limits in the remaining feasibility steps, then agree on any requirement gaps before implementation.

## Existing tools investigated

- The official Anki Python API exposes full collection download and ordinary media sync; the latter can upload changes and deletions. The [Anki manual](https://docs.ankiweb.net/syncing.html) likewise describes media sync as a merge even when collection sync is one-way. It does not meet the required media access restriction as a complete operation.
- [fastanki](https://github.com/AnswerDotAI/fastanki) provides a lower-level `SyncServer` transport that accepts an endpoint prefix and individual protocol method, handles zstd and HTTP 308, and exposes the response. The source reviewed at commit [`075c701ef2326516d0aa95c79812cd90d7fa7dd4`](https://github.com/AnswerDotAI/fastanki/blob/075c701ef2326516d0aa95c79812cd90d7fa7dd4/fastanki/syncer.py) declares version 0.0.7; the available PyPI version tested was 0.0.6. Its released code was also inspected locally. The package declares Python 3.11+, Apache-2.0 and alpha status, and depends on `fastcore`, `httpx`, `zstandard`, `protobuf>=6.31`, and `apsw`. Raspberry Pi availability and compatibility were not checked.
- An isolated local test (`/tmp/ankiweb-media-probe/fastanki_probe.py`) used **fastanki 0.0.6's transport**, a simulated 308 proxy and the official Anki 26.9.3 local server. The transport handled the redirect, after which a separate throwaway orchestration listed and downloaded 1,004 synthetic files in 42 ZIP requests, including a partial ZIP; all bytes and SHA-1 digests matched. Only the allowed media read methods reached the proxy during this download. Fixture setup used ordinary sync against the local server only. This tests the transport with custom control logic, not a finished fastanki backup feature or the actual AnkiWeb redirect. During setup, the proxy initially failed to forward the `anki-original-size` header; correcting the proxy made the same transport test pass.
- fastanki's high-level `Media.sync()` both fetches and sends changes. In the inspected 0.0.6 and 0.0.7 `_fetch_changes` source, each requested chunk produces one ZIP and the cursor is advanced to the last row even when fewer files were returned; there is no apparent retry of omitted names or comparison to the listing's SHA-1. An isolated runtime test of `_fetch_changes` in fastanki 0.0.6 with 1,004 synthetic files and a partial ZIP reproduced the issue: a ZIP contained two of four requested files; two files were missing while the local cursor advanced to USN 1004 (`/tmp/ankiweb-media-probe/fastanki_fetch_probe.py`). It must not be used as a complete backup operation without resolving and testing those gaps. Filename normalization can also create pending local deletions/uploads ([media source](https://github.com/AnswerDotAI/fastanki/blob/075c701ef2326516d0aa95c79812cd90d7fa7dd4/fastanki/media.py)).
- The inspected transport recursively follows 308 responses and reuses its authentication header for the new endpoint without an explicit redirect limit or destination validation in that code. Before any use with credentials, redirect limits, endpoint trust and credential handling require review and tests. The test proxy's 308 is not evidence that the real service emits the same redirect for every method.

No examined tool has yet been shown to satisfy the complete backup requirements on its own. The fastanki transport is a concrete candidate for protocol access; using it would still require substantial orchestration for paging, truncated batches, integrity, consistency, failures and safe output. No adoption decision has been made.

## AnkiWeb redirect without an account

On 2026-11-02, direct HTTPS POST requests to `https://sync.ankiweb.net/sync/meta` and `/msync/begin` using an explicitly invalid synthetic hkey each returned HTTP 403 without a `Location` header. No real account, password or collection was accessed. This attempt therefore did not observe an actual shard redirect. The Anki client and fastanki source both implement 308 handling, and the local proxy exercises a synthetic 308, but neither establishes the actual AnkiWeb response sequence for a valid account. Verifying that sequence without accessing an existing collection requires an independently provisioned test account; its setup and use, and any server-side effects, must be agreed with the user. Do not collect account secrets in the chat or substitute an unapproved sync.
