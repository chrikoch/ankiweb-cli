# Media pagination, package publication and Windows permissions

Investigated on 2026-11-03. Local probes ran on Linux x86_64, Python 3.13.5 and an ext4 filesystem, using synthetic data only. No Windows, macOS, Raspberry Pi filesystem or real AnkiWeb account was tested.

## Media pagination and count check

The inspected Anki server's `mediaChanges` query selects rows with `usn > ? LIMIT 1000` without an `ORDER BY`, although its schema contains an index on `usn` ([query](https://github.com/ankitects/anki/blob/29bb700b951e3f0c0cb69b77c0180fc1fe33e6ba/rslib/src/sync/media/database/server/entry/changes.sql), [schema](https://github.com/ankitects/anki/blob/29bb700b951e3f0c0cb69b77c0180fc1fe33e6ba/rslib/src/sync/media/database/server/schema_v4.sql)). SQLite explicitly says row ordering is undefined without `ORDER BY` ([SQLite SELECT](https://www.sqlite.org/lang_select.html#orderby)).

A local in-memory SQLite probe using the same query, schema shape and 1,004 shuffled rows selected the USN index. The normal query returned USNs 1 through 1000 in ascending order; with `PRAGMA reverse_unordered_selects=ON`, it returned 1004 through 5. This is a constructed SQLite test, not a claim that AnkiWeb enables that pragma. It demonstrates why the client must not rely on the observed normal order as a SQL guarantee. Rejecting non-increasing entries can catch the reversed result but cannot prove no lower-USN records were omitted: an arbitrary subset could itself be in ascending order.

The existing `/msync/mediaSanity` request is a useful additional candidate check. In the inspected server, it compares a supplied file count to the stored nonempty-media count in server metadata without a media upload or deletion request ([handler](https://github.com/ankitects/anki/blob/29bb700b951e3f0c0cb69b77c0180fc1fe33e6ba/rslib/src/sync/http_server/handlers.rs), [count check](https://github.com/ankitects/anki/blob/29bb700b951e3f0c0cb69b77c0180fc1fe33e6ba/rslib/src/sync/http_server/media_manager/mod.rs)). Local tests with Anki 24.11 and 26.9.3 each listed 1,004 synthetic files: the server returned `OK` for count 1,004 and `mediaSanity` for 1,003, with only allowlisted backup-side requests (`/tmp/ankiweb-media-probe/media_sanity.py`). Fixture uploads were confined to the local server. This can detect a count mismatch, but the stored count might itself diverge from the index. It does not prove the index reflects the entire physical server directory, verify file identities, establish an atomic snapshot, or prove AnkiWeb uses the same semantics.

## Publication without replacement

Prefer exposing the backup package under its final name only after it is completely written and closed. The user subsequently accepted an exclusive-copy fallback that can expose a partial final file when no safe no-replace publication method is available. A check such as `exists()` followed by `rename()` is not sufficient to prevent concurrent overwrite. POSIX `os.rename()` can replace an existing file, so it cannot by itself implement the no-overwrite requirement ([Python documentation](https://docs.python.org/3/library/os.html#os.rename)).

- On the local ext4 filesystem, a synthetic test of 12 simultaneous `os.link()` attempts to the same output name yielded one winner and 11 collisions; the winning complete bytes remained unchanged. [Linux `link(2)`](https://man7.org/linux/man-pages/man2/link.2.html) states an existing target is not overwritten. Hard links require a single filesystem and may be unsupported or disallowed by a filesystem.
- A separate 12-writer local ext4 test using Linux `renameat2(..., RENAME_NOREPLACE)` also produced one winner, 11 collisions and complete winning bytes. This Linux-specific primitive depends on kernel, libc and filesystem support; its documented supported filesystems include Linux vfat on sufficiently recent kernels ([rename(2)](https://man7.org/linux/man-pages/man2/renameat2.2.html)). It was **not** tested on vfat, network storage or the Pi.
- On Windows, [Python documents](https://docs.python.org/3/library/os.html#os.rename) that `os.rename()` raises `FileExistsError` if the target exists. On macOS, Apple documents a volume-dependent exclusive rename facility ([Apple documentation](https://developer.apple.com/documentation/foundation/urlresourcekey/volumesupportsexclusiverenamingkey)). Neither was tested here; no claim of safe publication on a particular Windows/macOS filesystem or network share follows from these references alone.

The proposed implementation should distinguish collisions from unsupported operations and other errors. If no no-replace publication operation is available, the user accepts copying into an exclusively created final name, with the documented risk of an incomplete file after interruption. This does not authorize overwriting an existing package or narrowing accepted output filesystems; exclusive-creation behavior still needs platform and filesystem verification.

## Windows credentials-file permissions

POSIX mode checks such as `0600` are useful for the Linux target. With Linux POSIX ACL semantics, the group bits represent the ACL mask, which limits effective access for named users and groups; see [acl(5)](https://man7.org/linux/man-pages/man5/acl.5.html). This does not establish the same guarantee on every filesystem. On macOS, ACLs can grant permissions beyond the POSIX mode bits ([Apple](https://developer.apple.com/library/archive/documentation/Security/Conceptual/AuthenticationAndAuthorizationGuide/Permissions/Permissions.html)). POSIX mode checks are not a Windows ACL validation. Python documents that Windows `chmod` changes only the read-only flag ([Python `os.chmod`](https://docs.python.org/3/library/os.html#os.chmod)); Windows file access is controlled using security descriptors and ACLs, often inherited from the parent directory ([Microsoft](https://learn.microsoft.com/en-us/windows/win32/fileio/file-security-and-access-rights)). Therefore `stat().st_mode` alone cannot establish that other Windows accounts cannot read a plaintext credentials file.

The user subsequently agreed to document user-managed restrictive permissions on Windows and macOS without automatic checks; incorrect permissions may go unnoticed. Linux still checks group/other mode bits. Group membership, inherited and explicit permissions, administrators and filesystem behavior affect what these checks can prove. No Windows or macOS runtime test was performed here.
