# Libraries for safe publication and credential-file permissions

Investigated on 2026-11-03. The publication probe ran only on Linux x86_64, Python 3.13.5 and ext4 with synthetic files. Other observations are based on the cited project source and documentation. No dependency has been selected or added to the project, and the requirement not to overwrite existing backups remains unchanged.

The searched candidates do not establish a ready-made method that satisfies the complete no-overwrite and no-partial-final-file requirements across all desired platforms and filesystems. This is not an exhaustive proof that no such library exists. Never silently use a check-then-rename fallback, or assume the documented Windows behavior covers every filesystem. See [platform and paging review](ankiweb-backup-platform-and-paging-review.md) for primary operating-system references and local primitive tests.

## Inspecting access permissions

- [`pywin32`](https://github.com/mhammond/pywin32/blob/a290c9a35fc031df082c25ebc5c76cdb2b5d67db/win32/src/win32security.i) exposes Windows APIs including `GetSecurityInfo` and `GetNamedSecurityInfo`; the project's [file security example](https://github.com/mhammond/pywin32/blob/a290c9a35fc031df082c25ebc5c76cdb2b5d67db/win32/Demos/FileSecurityTest.py) reads a security descriptor and its ACL. This is a **low-level building block**, not a verified one-call policy that establishes that only the intended user can read the credentials file. Defining effective-access policy, inherited and explicit entries, privileged accounts and behavior when ACLs are unsupported still requires design and Windows tests. No Windows runtime test was performed.
- [`pylibacl`](https://github.com/iustin/pylibacl) exposes POSIX.1e ACL manipulation through `libacl`; its README describes Linux and FreeBSD support and native library prerequisites. This is not demonstrated to handle macOS ACLs or Windows. It does not by itself define this project's effective-access policy and has not been tested on the target Pi.
- `0600` mode checks cannot be treated as a universal ACL check: macOS and Windows can have additional ACL-based access. See the [platform review](ankiweb-backup-platform-and-paging-review.md) for platform documentation. No examined library has been shown to provide a complete, tested, single cross-platform policy for this use case.
- On Linux filesystems implementing POSIX ACL semantics, the group mode bits correspond to the ACL mask when one exists; a zero group mask prevents named user and group entries from granting effective access. The other mode bits correspond to the other ACL entry. This makes a `0600` check meaningful for these ACLs without a separate ACL library, but does not establish equivalent behavior on every filesystem or operating system. See [acl(5)](https://man7.org/linux/man-pages/man5/acl.5.html).

## Proposed design for discussion

1. Export the complete package to a temporary file on the destination filesystem. Prefer a verified atomic no-replace publication operation. On a name collision, choose another name. Never fall back to checking for existence and then replacing the target. The user accepts an exclusive-create-and-copy fallback if no no-replace publication operation is available, with the possibility of a partial final file.
2. For Linux, evaluate `renameat2` as a small existing binding; verify installation on the Pi and test the intended destination filesystem. A hard link to the completed file is another candidate when no-replace rename is unavailable and links are supported. On Windows, [Python documents](https://docs.python.org/3/library/os.html#os.rename) that `os.rename` fails when the destination exists; its atomicity and relevant filesystem behavior need verification. macOS has an exclusive rename facility for volumes that support it ([Apple](https://developer.apple.com/documentation/foundation/urlresourcevalues/volumesupportsexclusiverenaming)); availability of a maintained binding and its behavior remain unverified. Windows and macOS require their own verified approach before claiming support.
3. On Linux, check the permissions of the opened credentials file and reject group or other access; document `chmod 600` and plaintext storage. Verify the assumptions for the actual filesystem. On Windows and macOS, the user agreed to documented user-managed restrictive permissions without automatic checks; document that incorrect permissions may go unnoticed.
4. Test competing processes, existing names, interrupted or failed exports and unsupported publication operations. Define the outcome when a post-publication directory sync fails, since the final file may already exist. Keep Raspberry Pi, reboot and real destination checks as acceptance tests.

This is a proposal, not an implemented or approved platform policy. It does not establish that the current requirements are met on all filesystems.

## Publication procedure and remaining decision

Candidate sequence for Linux, subject to approval and verification:

1. Create and fully validate a temporary package in the existing destination directory. Flush and close it before publication. Use a UTC timestamp and collision suffix for the proposed name.
2. Publish using `renameat2.rename(..., replace=False)` when supported. A destination collision chooses another name. When this operation is unavailable or unsupported, try creating a hard link from the complete temporary package to the final name; a successful link exposes the complete file without replacing an existing name. Then remove the temporary name. `boltons.fileutils.atomic_rename(..., overwrite=False)` is a candidate for this fallback after runtime testing. A collision again chooses another name. Other I/O errors are not evidence that a different publication mechanism will safely succeed.
3. If both methods are unavailable, exclusively create a new final name, for example with Python `open(..., 'xb')`, and copy the complete temporary file to it. On collision select another name. The user accepts that this exposes an incomplete `.colpkg` during copying and can leave one after interruption; report success only after copying and close succeed. Neither an existence check followed by ordinary rename nor a random name gives a no-overwrite guarantee. Exclusive-creation semantics require filesystem support; Linux documents limitations on older NFS configurations ([open(2)](https://man7.org/linux/man-pages/man2/open.2.html)).

This sequence describes proposed control flow, not an existing library that provides the entire sequence. The user approved the exclusive-copy tradeoff; exact implementation and library choices remain to be verified. On local Linux x86_64 ext4, a fresh test with 12 separate processes using `os.link` yielded one winner, 11 collisions, and intact winning bytes. Earlier local tests covered `renameat2`; neither test establishes behavior on the Pi, USB, NAS, macOS or Windows. NFS adds uncertainty: a failed rename may already have been performed by the server ([rename(2)](https://man7.org/linux/man-pages/man2/renameat2.2.html)). A post-publication cleanup or directory-sync failure may likewise leave a complete final file; the implementation must not blindly remove or overwrite it and must define how it is reported and retried.

A local ext4 probe using 12 processes and Python `open(..., 'xb')` produced one creator and 11 collisions, preserving the winner's bytes. A separate abruptly exited process left its partial final file visible, confirming the accepted limitation. This does not verify exclusive creation on the Pi, other operating systems or network filesystems.

Windows `os.rename` and macOS exclusive rename are candidates, not demonstrated cross-platform guarantees. On each supported platform, add concurrent-process, collision, interrupted-export and forced-unsupported-operation checks, and test actual destination filesystems before documenting their support. These checks must verify that the resulting package is complete and existing files survive. Do not claim universal filesystem coverage from a subset of tests.

## Consequence

For the actual Pi, a small approach built on established primitives may be sufficient if its output filesystem supports a suitable primitive, but this has not been verified on the Pi or on its intended backup destination. The current command specification requires an existing output directory; it does not authorize rejecting particular filesystems. The user expects operation beyond the Pi's local SD card and accepted exclusive-copy fallback when no atomic publication mechanism is available. Linux checks group/other permission bits; users manage Windows/macOS permissions themselves without an automatic check. The exact platform matrix and publication implementation remain open; extra substantial custom control logic needs agreement before implementation. Actual reboot, cron and AnkiWeb acceptance tests remain open.
